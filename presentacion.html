Semana 9 · El Problema Real

El Problema: Demasiados if/else para validar reglas

Antes, cada vez que queríamos cambiar una regla de pago o del comprobante, teníamos que editar código y reiniciar el servidor.

❌ Cómo estaba antes (Código Rígido):

Si queríamos validar qué comprobantes exigen voucher (Yape sí, Efectivo no) o el monto máximo, teníamos una cascada de if / else mezclada con la base de datos.

// Si cambiaba una regla, tocaba modificar código y recompilar: if (metodo !== 'EFECTIVO' && !tieneVoucher) { throw new Error("Falta voucher"); }
✅ Cómo lo resolvimos (Dirigido por Tablas):

Las reglas se sacaron del código y se pusieron en una tabla de configuración limpia. El código solo busca el método y lee sus reglas en $O(1)$.

// Ahora solo se busca en la tabla: const regla = TABLA_PAGOS[metodo]; if (regla.exigeVoucher && !tieneVoucher) ...
🗣️ Lo que puedes decir al profesor:
"Profesor, en lugar de llenar el servicio con condicionales if/else difíciles de mantener, aplicamos Construcción Dirigida por Datos (Semana 9). Separamos las reglas de negocio en una tabla limpia, reduciendo la complejidad ciclomática a una búsqueda directa en O(1)."
Semana 9 · Máquina de Estados (FSM)

El Semáforo del Gasto: Evitar Saltos Ilegales

¿Cómo evitamos que alguien confirme una cuenta y genere deudas si el OCR todavía no extrajo los datos o falló la lectura?

Los 4 Estados Reales de una Boleta en SplitVision:
📸 1. CARGADO
→
🔍 2. PROCESANDO (OCR)
→
🍽️ 3. EXTRAÍDO (Revisar)
→
💳 4. CONFIRMADO
Prueba de Protección en Vivo:

¿Qué pasa si intentamos saltar de [1. CARGADO] directamente a [4. CONFIRMADO]?

Código Real en el Backend:
// Archivo: src/common/fsm.ts export const RECEIPT_FSM = new StateMachine('Comprobante', [ { from: 'CARGADO', to: ['PROCESANDO'] }, { from: 'PROCESANDO', to: ['EXTRAÍDO', 'FALLIDO'] }, { from: 'EXTRAÍDO', to: ['CONFIRMADO'] }, { from: 'CONFIRMADO', to: [] } // Terminal inmutable ]);
🗣️ Lo que puedes decir al profesor:
"En lugar de validar estados con condiciones manuales en cada endpoint, usamos una Máquina de Estados Finitos (FSM). Previene transiciones ilegales por diseño en O(1). Si alguien intenta confirmar una boleta antes de extraer los datos, el autómata arroja 409 Conflict."
Semana 9 · Enlace Tardío (Late Binding)

¿Qué pasa si el motor de OCR local se satura con fotos borrosas y no queremos que los usuarios se queden esperando?

El caso real en SplitVision:

Tesseract OCR puede tardar varios segundos analizando una imagen. Si el servidor está bajo alta carga, podemos activar un interruptor de emergencia para pasar a modo manual sin reiniciar la app.

No se trata de instalar una herramienta externa, sino de programar el código para que nos diga exactamente qué le pasa.

📋

1. Historial Clínico

Logs en JSON con MDC

Anota quién hizo cada cosa, qué boleta tocó y qué IP usó, todo en una sola línea fácil de filtrar.

💓

2. Signos Vitales

Modelo RED

Tres números clave: cuántas peticiones llegan por segundo, cuántas fallan y cuánto demoran.

🩻

3. La Resonancia

Trazas OpenTelemetry

Sigue una solicitud desde que el usuario hace clic hasta que termina de guardarse en PostgreSQL.

Semana 10 · Contexto de Diagnóstico (MDC)

Logs Estructurados: Cómo sabemos quién hizo qué

En lugar de imprimir texto suelto que nadie puede buscar, generamos eventos en JSON estructurado.

Un Log Real emitido por SplitVision:
{ "timestamp": "2026-11-20T21:10:05.120Z", "level": "INFO", "event": "payment.create", "trace_id": "8a3c60f7-b24a-4e92", "user_id": "andres_01", "ip_address": "192.168.1.15", "amount_cents": 3500, "method": "YAPE" }
¿Cómo viaja el contexto sin ensuciar el código?

En Java se usa MDC de Logback. En Node.js usamos AsyncLocalStorage de la biblioteca oficial.

Cuando entra una solicitud HTTP, se guarda el trace_id e IP en el hilo asíncrono. Cualquier servicio puede hacer logger.info() y los datos viajan solos.

🧪 Verificado en test unitario: test/telemetry.test.ts
🗣️ Lo que puedes decir al profesor:
"Implementamos el patrón Mapped Diagnostic Context (MDC) usando AsyncLocalStorage. Esto inyecta automáticamente el trace_id, user_id e IP en cada log sin tener que pasar esos parámetros manualmente por cada función."

Podemos calcular más de 16,000 repartos completos por segundo. Cero fugas de memoria detectadas.

Script ejecutable: scripts/benchmark-profiling.js
Lectura del Flame Graph (¿Dónde se gasta el tiempo?):
Base de Datos PostgreSQL (Transacción I/O) 85%
Cálculo Matemático en CPU (Hamilton) 15%

Diagnóstico: El cuello de botella no es la CPU (toma menos de 0.1 ms). El tiempo real está en el I/O con PostgreSQL, lo que valida usar transacciones cortas con SELECT FOR UPDATE.
