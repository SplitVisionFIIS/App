Semana 9 · Principio Arquitectónico

Lógica Imperativa vs. Construcción Dirigida por Datos

En lugar de preguntarnos '¿Qué código debemos escribir?', preguntamos '¿Qué configuración debemos leer?'

❌ Antes: Cascada Imperativa if/else/switch
src/modules/pagos/pagos.service.ts (Antiguo)
if (method !== 'EFECTIVO' && !hasEvidence) { throw validation('Evidencia obligatoria'); } else if (method === 'PLIN' && amount > 150000) { throw validation('Excede límite diario PLIN'); } else if (receipt.status !== 'EXTRAÍDO') { if (receipt.status === 'CONFIRMADO') throw conflict('Ya confirmado'); throw conflict('Estado no permite reparto'); }

Alta complejidad ciclomática. Exige recompilar y redesplegar ante cada cambio de regla.

✅ Ahora: Búsqueda O(1) en Tablas + FSM Declarativa
src/modules/pagos/pagos.service.ts (Actual)
// 1. Reglas en O(1) desacopladas del motor const rule = validatePaymentByRules(method, amountCents, ref, hasEvidence, isPlinActive); // 2. Transición validada matemáticamente por FSM RECEIPT_FSM.assertTransition(receipt.status, 'CONFIRMADO', receiptId);

Complejidad ciclomática = 1. Reglas modificables en tiempo de ejecución (Late Binding).

Semana 9 · Máquinas de Estado Finito

Máquinas de Estado Finito (FSM) como Mecanismo de Control

Previene transiciones ilegales por diseño en O(1), convirtiendo reglas de negocio ambiguas en topologías matemáticas exactas.

Los 3 Principios de la FSM (Diapositiva 4)
  • Comportamiento por Estado: Las operaciones permitidas están dictadas estrictamente por el estado actual.
  • Restricción Matemática: Elimina la necesidad de validar el estado previo con if/else en cada función.
  • Construcción Segura: Si una transición no está en la tabla, arroja 409 Conflict instantáneo.

export const RECEIPT_FSM = new StateMachine<ReceiptFsmState>('Comprobante', [ { from: 'CARGADO', to: ['PROCESANDO'] }, { from: 'PROCESANDO', to: ['EXTRAÍDO', 'FALLIDO'] }, { from: 'EXTRAÍDO', to: ['CONFIRMADO', 'FALLIDO'] }, { from: 'FALLIDO', to: ['PROCESANDO', 'EXTRAÍDO'] }, { from: 'CONFIRMADO', to: [] }, // Estado terminal inmutable ]);

Semana 9 · Table-Driven Design

Construcción Dirigida por Tablas (O(1))

Reemplazar bifurcaciones complejas con búsquedas directas en diccionarios estructurados.

Ventajas en SplitVision (Diapositiva 6)
  • Acceso Directo O(1): En lugar de evaluar 5 condiciones booleanas secuenciales, se indexa PAYMENT_RULES_TABLE[method].
  • Desacoplamiento: Las reglas de negocio (montos máximos, necesidad de voucher) están separadas de la ejecución.
  • Evolución Segura: Agregar Plin, Yape o ApplePay sólo requiere una nueva fila en la tabla.

Semana 10 · MDC (Mapped Diagnostic Context)

Logs Estructurados e Hiper-contextualización

El MDC funciona como un pasaporte de datos adherido al hilo asíncrono para indexación inmediata.

Log JSON emitido en producción
{ "timestamp": "2026-11-20T21:05:14.210Z", "level": "INFO", "event": "payment.create", "trace_id": "8a3c60f7-b24a-4e92-bc91-235123d", "user_id": "usr_7714", "tenant": "event_9912", "ip_address": "192.168.1.15", "amount_cents": 4500, "method": "YAPE" }
Implementación Técnica (Semana 10 · Diapo 3)

En Java se usa org.slf4j.MDC. En Node.js/NestJS utilizamos AsyncLocalStorage de la API nativa de Node.

El middleware inyecta el trace_id e IP al recibir el request. Cualquier función que invoque logger.info() hereda el contexto sin pasarlo como argumento.
